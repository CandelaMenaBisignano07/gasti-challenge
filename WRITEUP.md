# Writeup — Proceso

## Cómo me metí en Mastra

Primero, antes de leer las docs, chequee si habia un mcp de mastra para agilizar el desarrollo y lo conecte. 


Despues, use Agent de Mastra con instructions para que el request context que contiene las categorias y el dia como parametros importantes esten al dia en cada iteracion. Tambien use createTool con los schemas de Zod que esta adentro de un factory que genera una tool que llama al gateway directamente y ademas hace el handle de los errores que pueda llegar a tener el llm. Ademas, cada tool tiene una prop que viene ya en Mastra que nos ayuda a normalizar el output de la tool si nosotros lo definimos cuando creamos la gateway tool.

Otra de las primitivas que use fue Memory, en la cual trabaje tres partes de la memoria: lastMessages en el que esta el context corto en el que actualmente soporta una ventana de 10 mensajes, semanticRecall para que se acuerde de los 2 mensajes mas importantes en ventanas de 2 mensajes (claramente primero se vectorizan los mensajes, ese handle lo hacemos con libSQLStore, el adapter de Mastra que soporta files .db en local) y workingMemory en la que guardamos PARA QUE EL AGENTE TENGA ESTA INFO A MANO EN SU CONTEXTO goals, ingresos, presupuestos y nombre del user, esta info igualmente se guarda en db y hay una tool que mantiene en sync la working memory (updateWorkingMemory). 

Por ultimo, usamos el cliente de Mastra en el endpoint dentro de next (no lo inclui en la app de api para no manejar problemas de cors y respetar dominio) para poder exponer el agente y streamear las respuestas.

Lo que creo que mas me costo fue pivotear el tema del webhook de mp, porque queria buscar librerias que ya resolvieran el tema de integrar billeteras, que haya ese auth y expongan algun webhook por que queria evitar tmb volver a integrar mp y ademas no queria llegar a la instancia de hacer polling, pero como no habia ninguna libreria que haga eso y opere en Argentina tuve que optar por el polling. Tambien me costo un poquito la decision de si usar db en files o usar jsons y listo. Me parecio raro que no tuvieran un adapter que se maneje en ram como el de langgraph y como me acostumbre a usar ese en entornos de desarrollo fue como salir de la zona de comfort, pero siempre eso es algo bueno.

## Investigacion de otras herramientas y por que se descartaron.

Antes habia diseñado la integracion proactiva de mercado pago para que sea push-driven, sobre webhooks que mandaran notificaciones sobre el evento `payment` que supuestamente te notifica. Lo implemente, lo probe e2e con cloudflare y transacciones reales, pero despues me di cuenta que el webhook de `payment` solo dispara para movimientos creados por productos de integración (Checkout API / Bricks / Subscriptions / Wallet Connect). Las cosas que un usuario de finanzas personales realmente tiene en su cuenta, o sea, transferencias P2P, dinero en cuenta, pagos recurrentes desde MP, compras en comercios, no generan ninguna notificación, pero la api de `/v1/payments/search` con el mismo token si las devuelve.  Pero antes de pasar al polling estuve un rato mirando librerias para resolver el problema de leer movimientos de varias plataformas con un solo provider y de paso tener webhooks ya resueltos y no tener que hacer polling, pero ninguno cubría Argentina: **Plaid** no opera en Argentina, **Belvo** sí opera en LATAM pero cuando chequee la lista de instituciones argentinas era bastante chica, **Pluggy**.Esto me hizo entender que mp con polling era lo mejor para la v1 por que tiene una api muy completa, un mcp server que ayuda con el desarrollo y ademas es la que mas se usa y con la que iba a poder testear mas facil.

## Metodología de trabajo con IA

Para trabajar mano a mano con claude me ayude con superpowers como pipeline, que ya integra todo el workflow entero: specs, planes, subagents nuevos para cada tarea, testing, review del codigo y pushearlo. Ademas labura con worktrees que ayudan un monton a acelarar el desarrollo. Ademas, antes de eso claramente arme el CLAUDE.md hablando del stack, arquitectura, obligarlo a seguir el workflow de superpowers con cada feature y algunas otras especificaciones para que use determinadas skills en determinados momentos. Despues, me parecia super importante poner foco en el producto, asi que arme un PRODUCT.md que creo que lo arme con una skill que se llama product-brainstorming, que me ayudo a definir mas que nada el scope del producto, y eso me sirvio despues en muchas features en las que yo creia que valia la pena meter pero al haberlas delimitado en el PRODUCT.md me bajaba a tierra devuelta al scope en el que estaba. Tambien agregue un DESIGN.md para que cada componente que fuera a crear estuviera alineado a mi design system.
